Overview

Index Health is a fitness and wellness web app built around one number: the Index Score, a 0–100 aggregate of tracked health metrics across sleep, recovery, nutrition, body composition, and training load. The live site is a portfolio demo only: visitors explore the full UI through demo mode, which loads a deterministic 90-day synthetic dataset (fake persona, fake metrics, fake league). Public sign-ups are closed — I am not operating this as a health data service and do not store visitors' real health data.

The Index scoring pipeline

End-to-end flow from log ingestion through normalisation, weighted aggregation, score caching, and UI replay. On the public demo, every step runs against synthetic data — History and Today always agree on a given day's score because they share the same computeIndex function.

  1. Ingest. In demo mode (the default visitor path), a seeded 90-day synthetic HealthDataset replaces all Supabase reads. Log forms exist in the UI but writes are blocked on the live demo.
  2. Validate. logValidation.ts enforces physiological bounds and date guards on every write. Invalid values are rejected before they can corrupt the score or charts.
  3. Persist. The codebase includes a Supabase Postgres layer with RLS, but the public deploy does not accept sign-ups or persist visitor data. Demo mode is read-only throughout.
  4. Normalise to sub-scores. computeIndex() maps each present metric to a 0–100 sub-score using age/sex-aware population reference ranges (HRV, RHR, VO₂ norms) or user-specific targets (weight vs goal, calories vs daily goal). BMI is calculated from latest weight and profile height. Workout frequency uses a 7-day rolling window.
  5. Aggregate. Weighted mean over present metrics only. A coverage ceiling (min(100, 58 + tracked × 7)) caps the achievable score when few metrics are tracked. Confidence = tracked / 6. Absent metrics are excluded, not penalised as zero-weight.
  6. Cache for social. In a live account, clientData.ts would recompute the score and upsert user_score_cache for leaderboard queries. Demo mode fakes the league table from synthetic data instead.
  7. Display and replay. Today dashboard shows hero score, confidence bar, driver cards, and coaching tips. History replays computeIndex as-of each logged day. Metrics drills into per-metric series, live Pearson correlations, and distribution histograms.

Nine metrics currently feed the score (HRV 14%, Sleep 14%, Resting HR 10%, Workouts 10%, Steps 8%, Calories 6%, Weight 6%, Run/cardio 5%, BMI 4%). VO₂ Max and TDEE slots are reserved but display-only today — estimated values are computed for the UI and deliberately excluded from the Index to avoid double-counting RHR.

Engineering decisions

Scoring engine design

ProblemA single health number is easy to game or misread if the model is opaque, if missing data is treated as zero, or if estimated metrics double-count real inputs.
ApproachcomputeIndex() is the single source of truth with public METRIC_WEIGHTS, explicit per-metric lerp() reference functions, a present flag per metric, and a coverage ceiling so one strong cherry-picked metric cannot read as a top Index. VO₂/TDEE stay display-only.
OutcomeTested scoring with bounded 0–100 guarantees, graceful degradation, and an inspectable driver breakdown on the dashboard.

Static export architecture

ProblemShip a Next.js app to Vercel static hosting and Capacitor native shells without a Node server, while the codebase still explores browser-side data patterns.
Approachoutput: 'export' in next.config.ts. All data fetching and mutations run in the browser via @supabase/supabase-js. The actions/ folder holds client-callable async functions, not server actions.
OutcomeOne build artefact (out/) serves web (Vercel) and native (Capacitor webDir: 'out'). Tradeoff: no SSR, no API routes, CSP requires unsafe-inline for scripts/styles.

Demo-only data on the live deploy

ProblemShowcase a convincing health product UI without collecting or storing real visitor health data.
ApproachDemo mode returns a seeded 90-day synthetic HealthDataset (fake persona, metrics, and league). Sign-ups are closed; writes are blocked. The codebase also has a showcase decrypt path and Supabase fetchers for architecture exploration, but the public demo path is synthetic only.
OutcomeRecruiters can explore the full app with zero account and zero real health data involved.

Supabase schema, RLS, and score cache

ProblemIf this were a real multi-user health app, social features would need to expose scores without leaking underlying logs.
Approach9 Postgres tables + 2 views in the repo, all RLS-scoped to auth.uid(). Social layer designed to expose only user_score_cache fields for opted-in users. Not exercised on the public demo.
OutcomeSchema and RLS patterns are in the codebase as an architecture exercise; the live deploy runs on fake data instead.

Privacy / social layer

ProblemSocial comparison needs a single comparable number without exposing underlying health records.
ApproachOpt-in via social_opted_in (Settings + Sources). Friends see Index Score cache only. buildLeague() falls back to global top-10 when no friends exist.
OutcomeWorking friends flow (search, request, accept/decline) with minimal data surface. Demo mode fakes a 5-person league for screenshots.

Hand-rolled SVG charting

ProblemChart libraries add bundle weight and fight the brutalist flat design; static export limits server-side rendering tricks.
ApproachCustom SVG in TrendChart.tsx, inline mini charts in History/Metrics/Dashboard. Score history replays computeIndex per day rather than caching a separate series.
OutcomeZero chart-library dependency. History and Today always agree on the same date's score.

Closed sign-ups, demo-first entry

ProblemPortfolio demo must not accept public accounts or store real health data from visitors.
ApproachPublic sign-ups are disabled. Landing and login CTAs launch demo mode with synthetic data. Auth UI exists in the codebase for development, but visitors never need credentials.
OutcomeThe live site is unambiguously a demo — not a consumer health data product.

Testing and verification

ProblemScoring, crypto, and validation logic must be defensible in a hiring conversation without manual QA alone.
Approachpnpm test runs 10 files via Node's built-in node:test (indexScore, derived, suggestions, logValidation, records, units, league, goalProgress, showcaseCrypto, utils).
OutcomeCore algorithms have automated coverage. No CI workflow in repo; no E2E browser tests.

Graceful degradation when integrations fail

ProblemWearable OAuth is not live; users will have partial datasets for months in a real launch.
ApproachScoring excludes absent metrics, caps score by coverage, shows confidence UI. Sources page marks all non-manual integrations as "Planned." provider-sync Edge Function exists server-side but client connect/sync was removed.
OutcomeDemo mode stays fully usable with synthetic partial datasets. Missing integrations show as empty metric slots, not broken screens.

Features

  • Demo mode (default): deterministic 90-day synthetic persona with fake metrics across all screens
  • Index Score hero on Today dashboard with tier ramp, 1d/7d/30d deltas, and logging streak
  • Confidence indicator showing how many metrics back the current score (6-signal calibration target)
  • Per-metric driver cards ranked by Index impact and rule-based coaching tips
  • Metrics screen: trend chart, Pearson correlations, distribution histogram — all from synthetic demo data
  • History: 90-day Index score chart replayed from demo logs, personal records, range selector (1W–1Y)
  • Social: fake 5-person league table in demo mode (friend search and real accounts not active publicly)
  • Log, Settings, and onboarding UI shells (writes blocked on the live demo; sign-ups closed)

Status

Index Health is a 2026 portfolio demo: a statically exported Next.js fitness app with a tested scoring engine and full product UI. It ships live at index-health.dev; source is on GitHub. The live deploy runs on synthetic demo data only — public sign-ups are closed and I do not store visitors' real health data.

What is shipped for the demo: the full UI shell, Index Score computation with missing-data rules, deterministic 90-day fake dataset, social league UI with synthetic standings, and unit-tested core libraries. What is not: a live consumer health data service, wearable OAuth, App Store submission, or production operation of the Supabase backend for public users.

The technical highlight is the scoring pipeline: a single pure function (computeIndex) with public weights, explicit presence semantics, coverage capping, and day-replay consistency across Dashboard, Metrics, and History — all exercisable on fake data without touching a real database.

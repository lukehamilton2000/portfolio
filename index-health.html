Overview

Index is a fitness app built around one number: the Index Score (0-100). Sleep, HRV, resting heart rate, steps, workouts, calories, weight, BMI, and a few related metrics all feed into it. The UI is dark, sharp-cornered, and a bit instrument-panel. Charts are hand-rolled SVG.

This is a portfolio project, not a product with real users. Health data is special-category under UK/EU GDPR, so I closed public sign-ups on purpose. I am not collecting strangers' metrics for a showcase app. The live site uses synthetic demo data; I can also unlock an encrypted dump of my own history. That is a deliberate call, not half-finished auth.

Scoring pipeline

Most of the work that matters sits in computeIndex(). It is pure and unit-tested. You hand it a day's metrics and get a 0-100 score plus a short breakdown of why. Today, Metrics, and History all call the same function so the number does not drift between screens.

How the Index Score is calculated
Day's metrics
sleep, HRV, RHR, steps, workouts, calories, weight, BMI, …
Drop missing ones
absent metrics are skipped, not treated as zero
Score each 0-100
age/sex refs for HRV and RHR, goals where they apply
Weighted mean
only over metrics that actually have values
Coverage cap
track almost nothing, and the max score drops with it
Index Score 0-100
plus confidence, plus explainScore for "Why this score"

History runs the same function day by day. Charts use daily points for about the last 90 days, then weekly samples so long ranges stay usable.

  • Missing metrics are left out of the average. They do not count as zero.
  • If you only log one or two things, the coverage cap stops the score looking absurdly high.
  • explainScore ranks what moved the number so the UI can show "Why this score".
  • Related logic (validation, units, suggestions, records) is pure and covered by node:test.

Engineering decisions

Closed sign-ups, full demo

ProblemShipping this as a real multi-user health product means policies, compliance work, and handling special-category data. That is a lot of overhead for a portfolio piece.
ApproachNo public sign-up. Visitors get synthetic data. I can decrypt my own encrypted history with a passphrase. The Supabase + RLS path is in the repo for real accounts, but it is not open to the public.
OutcomePeople can still walk the whole UI. I am not sitting on other people's health data.

Static export + Capacitor

ProblemI wanted one build for the web and a native shell, without running a Node server just to host it.
ApproachNext.js with output: 'export'. Data work happens in the client. Capacitor points at out/.
OutcomeDeploy is simple. The downside is no classic server actions. If accounts were live, writes would go client-side under RLS.

No Tailwind / component library

ProblemI wanted a flat, instrument-panel look and did not want to fight a UI kit to get there.
ApproachPlain CSS with custom properties. Charts are custom SVG in TrendChart, with normal HTML labels so axis text is not stretched.
OutcomeLess dependency weight, and the charts behave the way I want.

Interview talk track

Rough script if I am clicking through the demo:

  1. Health stuff is scattered. I wanted one daily number, and a clear reason for it.
  2. I closed sign-ups because I am not taking other people's health data for a portfolio app. Demo data instead.
  3. Scoring is one pure function: sub-scores, weights, coverage cap, then "Why this score".
  4. Today and History share computeIndex, so the charts match the hero number.
  5. CSS tokens and custom SVG charts. No Tailwind or shadcn.
  6. Static export plus Capacitor. Wearables and social are intentionally unfinished on the public build.

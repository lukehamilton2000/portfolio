Overview

SpellType is an audio-first spelling trainer, inspired by MonkeyType. It reads a word aloud, you type it, and you get instant per-letter accuracy feedback. The whole thing is keyboard-first and built around a tight "one more round" loop — minimal UI, a 3-2-1 countdown, and immediate results so you can practise spelling fast.

This page is less about the feature list and more about the decisions behind it: where I had to choose between the flashy option and the one that actually shipped well, and what each choice cost or saved.

The voice pipeline

This was the most interesting rewrite in the project, so I'll lead with it. The whole app depends on words being read aloud — clearly, instantly, at a speed the user controls. My first version got the quality right but everything else wrong.

Re-architecting from live TTS to pre-rendered audio

ProblemI started with live in-browser neural TTS — an ONNX model running via WebAssembly, roughly 400MB. It loaded slowly and janked the UI, because synthesis ran on the main thread and blocked rendering every time a word was spoken.
ApproachI diagnosed the root causes and moved synthesis offline. A Node script now runs the same neural model once, ahead of time, over all ~1,800 words and encodes them to MP3. The app ships those as ~22MB of static files behind a manifest, with the browser's built-in voice as a fallback. Per-word speed is handled at playback time via HTMLAudio playbackRate, so I only need one recording per word instead of re-synthesising for each speed.
OutcomePlayback is instant and jank-free, the ~400MB download is gone (down to ~22MB of static assets), audio quality is unchanged, and speed control stayed flexible. I chose the pragmatic architecture over the flashy one — and the app is better for it.

Engineering decisions

A few more calls I'm happy with, each framed the same way — the problem, what I did, and what it bought me.

Reliable audio autoplay on mobile

ProblemiOS and Android block audio that doesn't originate from a user gesture. The first word plays after a 3-2-1 countdown — by which point the tap that started the round is "over", so the browser silently refuses to play it.
ApproachI keep a single persistent <audio> element that I "unlock" inside the user's tap gesture, then reuse it for every word in the session instead of creating new elements.
OutcomeThe countdown-delayed first word plays reliably on mobile, where the obvious implementation fails silently.

Server-side scoring and anti-cheat

ProblemThere's a public leaderboard, so client-reported scores can't be trusted — anyone can edit a network request.
ApproachScores are recomputed and validated on the server; client values are never trusted. I added DB-backed rate limiting, same-origin CSRF guards, and routed every public response through a single "public user projection" helper so private fields can't leak by accident. I ran a full security and cost review before launch.
OutcomeA leaderboard you can actually trust, and one place to reason about what's safe to expose.

Privacy-conscious social layer

ProblemAn accuracy-ranked leaderboard and public profiles are fun, but they're an easy way to leak personal data you didn't mean to share.
ApproachEverything public is opt-in: a chosen handle instead of a real name, an avatar shown only if the user enables it, and no per-word or per-answer data ever exposed.
OutcomeA social layer that's safe by default and only ever shows what a user has explicitly agreed to.

SEO as a growth engine

ProblemA niche tool needs a way for people to find it that isn't "I told my friends".
ApproachI statically render ~1,800 "how to spell X" pages — one per word — each with its own audio and a direct path into the game, plus a generated sitemap.xml and robots.txt.
Outcome~1,800 indexable entry points into the app, each useful on its own and each a doorway into the practice loop.

Resilience and graceful degradation

ProblemA serverless app shouldn't fall over because a database is slow, exhausted, or simply not configured.
ApproachThe app runs even with no database configured (guest mode carries the experience), and database access uses pooled connections sized for serverless Postgres.
OutcomeThe core experience degrades gracefully instead of breaking, and connection limits don't bite under load.

Features

  • Audio-first loop with per-letter feedback and a 3-2-1 countdown
  • Word lists by category — common misspellings, frequency tiers, difficulty from easy to insane
  • Homophone hints that show the meaning, not the spelling, so they never give the answer away
  • Guest mode via localStorage, plus cloud sync when signed in
  • Accuracy-ranked leaderboard, public profiles, and a stats dashboard with charts
  • User-controlled playback speed and a browser-voice fallback
  • A flat amber-on-charcoal theme inspired by MonkeyType

Overview

Voronoi Mosaic is a browser-based image stylization tool: upload a photo and it becomes a mosaic of Voronoi cells, each colored from the pixels inside it. Sliders control how many cells you get, how seeds are placed, how colors are sampled, and whether cells have borders, then export a PNG at up to 8K or dump the seed layout as JSON.

Under the hood it's computational geometry (Delaunay/Voronoi, Lloyd relaxation), image processing (Sobel-guided placement, per-cell color stats), and deliberate performance caching so 2,000 cells on a 4K source stays usable. The rest of this page covers how it's built.

The mosaic pipeline

Each regeneration runs the same sequence: geometry and color are cached where possible so only the affected pass reruns.

  1. Decode the uploaded image to a capped sample surface
  2. Place seeds: random, jittered grid, or edge-weighted via a Sobel magnitude field
  3. Build a Delaunay triangulation, then derive the Voronoi diagram with d3-delaunay
  4. Optionally run Lloyd relaxation (0–5 passes) for more uniform cell shapes
  5. Sample per-cell color: average, median, or dominant
  6. Paint filled cells on Canvas 2D; borders are a separate stroke pass
  7. Export PNG at the chosen resolution, or JSON of seed and cell data

Engineering decisions

Voronoi geometry at scale

ProblemUp to 2,000 cells on large canvases (4K source, render scale 2) must stay interactive while sliders change.
Approachd3-delaunay for Delaunay/Voronoi construction; nearest-seed queries via delaunay.find with hints, not brute-force per pixel; Lloyd relaxation rebuilds the diagram per iteration.
OutcomeSmooth cell-count and relaxation controls without freezing the UI.

Edge-weighted seed placement

ProblemRandom and jittered layouts ignore image structure, so detail gets lost in flat regions.
ApproachA coarse Sobel edge-magnitude field biases seed placement toward high-contrast regions; a deterministic PRNG reproduces layouts per seed value.
OutcomeDetail-aware mosaics on structured photos.

Render pipeline caching

ProblemRecomputing geometry and per-cell color on every border, background, or zoom tweak is wasteful.
ApproachCache geometry and color on a key that excludes border, appearance, and render-scale-only changes; borders and background only re-stroke or refill; viewport zoom is CSS-only and does not invalidate the heavy pass.
OutcomeSlider drags and zoom stay responsive at the heaviest workload (2,000 cells, 3840×2160 source, render scale 2).

Canvas 2D over SVG/WebGL

ProblemSVG and WebGL look attractive for visual apps, but add complexity for a mostly static render.
ApproachCanvas 2D: one fill pass for up to 2,000 cells; color sampling is a one-time cached preprocess, so WebGL setup adds cost without per-frame shader benefit.
OutcomeSimpler pipeline; measured performance budgets passed.

Schema-driven product shell

ProblemMany controls must map cleanly to runtime state and export.
ApproachToolcraft runtime: declarative schema drives controls; custom canvasContent renderer; sticky footer export; standard PNG export helper with 2K/4K/8K resolution.
OutcomeEvery visible control affects observable output; reset and export covered by acceptance tests.

Testing discipline

ProblemVisual and interactive apps regress easily.
ApproachVitest for engine, schema, and scenarios; Playwright browser acceptance for upload/transform/clear, controls, and export; declared performance scenarios with stress fixtures.
Outcomepnpm verify:final gate covering docs integrity, unit tests, build, browser acceptance.

Features

  • Upload source image with rotate/flip transforms
  • 20–2,000 Voronoi cells: Random / Jittered / Edge-weighted distribution
  • Lloyd relaxation (0–5 passes)
  • Per-cell color: Average / Median / Dominant
  • Optional cell borders (width, stroke color/opacity)
  • Regenerate seed layout on demand
  • PNG export at 2K / 4K / 8K; JSON export of seed/cell data
  • Canvas zoom, undo/redo, theme toggle
  • Background include toggle for PNG export preview
